# Secure login foundation (not activated)

This branch adds an isolated Better Auth 1.7.18 Worker. It does not change the live mock, deploy login, provision D1, create provider applications, or connect browser sessions to MCP. There is no login UI yet. `/account` returns a minimal JSON identity for a signed-in, admitted user.

## Implemented boundary

- Google and GitHub are configured only when both provider settings exist. No passwords, direct ID-token submissions, user-selected callback URLs, public invite administration, linking, unlinking, or email changes.
- Verified, currently invited email required on creation and every OAuth sign-in. Stable library user IDs plus unique provider/subject pairs identify accounts; email is admission, not a tenant ID. Implicit linking is disabled, including same-email identities.
- Better Auth handles OAuth state, browser binding, code exchange and session signing. Host-only `__Host-` secure HttpOnly SameSite=Lax cookies, database sessions, no cookie cache, eight-hour absolute lifetime and five-minute fresh-session window.
- The app rechecks current admission on every account request. Revoking an invite blocks existing sessions immediately. Operator revocation must also delete that user's sessions before any later reinstatement, so reinstatement cannot revive an old cookie.
- Same-origin JSON POST required for login/logout/revoke. Exact HTTPS origin, allowlisted endpoints and bounded inputs; no dynamic host trust or external redirects.
- OAuth access/refresh/ID tokens are cleared by database hooks. No session IP, user-agent or profile image retained. Logs and traces remain off pending a redacted observability design.
- Rate-limit keys are purpose-tagged HMAC digests of the library's client-IP/path key. D1 UPSERT atomically caps concurrent admissions. These pseudonymous buckets are still metadata. Expired buckets, OAuth verification records and sessions are cleaned by the scheduled handler. **Provision a scheduled trigger before activation**; none is provisioned in the disabled config.
- Logout and all-session revoke await database deletion before clearing the cookie. A database failure fails closed with503. This cannot guarantee deletion during an outage; callers must retry after recovery. No successful response is sent by the wrapper before deletion.
- Browser cookies never authorize `/openrouter` or MCP. MCP OAuth audience, consent, scopes and tokens are a separate unreleased component.

## Local verification

`npm run check` includes typecheck and workerd/local D1 tests. Provider HTTP responses are mocked, not real accounts or credentials. Tests cover GitHub admission, unverified/uninvited rejection, returning-provider verification, state cookie mismatch and replay, same-provider/different-subject collision, two-user isolation, cookie fixation resistance, token stripping, expiry, logout, all-session revocation, input/origin guards, log redaction and concurrent rate-limit buckets.

`npm run check:auth` bundles the isolated Worker and executes it under Miniflare to verify disabled-by-default behavior. CI runs both commands. Google code is configured through the vetted adapter but **Google callback integration and real-provider browser tests are not qualified yet**. Nor are Dots/Vocs Code MCP OAuth, cross-site browser behavior, outage injection, production concurrency or full account recovery.

## Schema and configuration

`migrations/auth/0001_better_auth.sql` is generated by the installed library via `node scripts/generate-auth-schema.mjs` on Node24. `0002_admission.sql` adds invitation admission, a unique provider-subject index and private rate-limit buckets. Never run either against an existing VocsCode database. Use a separately approved D1 database and reviewed migrations.

Required activation inputs: `AUTH_ENABLED=true`, exact `AUTH_ORIGIN`, `AUTH_DB`, a high-entropy `AUTH_SECRET` stored through an approved secret flow, and configured provider ID/secret pairs. The public repo contains no real credentials. `wrangler.auth.jsonc` intentionally has no routes, D1 binding, OAuth settings or enabled flag. Creating credentials, routing and activation require separate approval and the gates in LOGIN-RELEASE-PLAN.md.

This is a backend foundation ready for further review, not a claim of production authentication readiness.
